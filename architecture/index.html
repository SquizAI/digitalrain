2. Architecture Overview

DigitalRain is a macOS desktop utility that renders a Matrix-style "digital rain" animation as a live wallpaper behind all other application windows. It is built entirely with Electron v28 and uses the HTML5 Canvas 2D API for rendering.

The architecture is a classic two-process Electron app. The main process (main.js, 527 LOC) manages the application lifecycle: it creates one BrowserWindow per connected display, positions each window at desktop level (below all apps, above the wallpaper), configures a system tray icon with a context menu, registers global keyboard shortcuts, and monitors for display configuration changes.

The renderer process (matrix.js, 734 LOC) runs inside each BrowserWindow and drives a canvas-based animation loop at 30 FPS, rendering falling columns of Katakana characters interspersed with AI/ML terminology using a typing-decryption visual effect.

The app has zero external runtime dependencies. All rendering is done with built-in browser APIs. The only npm packages (electron, electron-builder, canvas) are devDependencies. The entire codebase fits in two JavaScript files, one HTML file, and one CSS file.

5. Data Model

This app has no database. All state is held in memory as JavaScript objects.

CONFIG (immutable, matrix.js:61-87): Animation settings including FPS target, font sizes, drop density, typing speed, and visual toggles.

Drop (mutable, matrix.js:208-258): Each falling column. Contains position, speed, text content, typing state machine state, trail characters, base color, pulse phase, and an encrypted character cache.

BrowserWindowConfig (per-display, main.js:87-103): Frameless, non-transparent window matching each display's bounds.

8. Sequence: Animation Render Loop

Per-frame render cycle
sequenceDiagram
    participant RAF as requestAnimationFrame
    participant Draw as draw function
    participant Canvas as Canvas 2D Context
    participant Drop as Drop Object
    participant State as Typing State Machine

    RAF->>Draw: currentTime
    Draw->>Draw: Check paused flag
    Draw->>Draw: Frame rate limiter 1000/30ms
    Draw->>Draw: Calculate deltaTime clamped
    Draw->>Canvas: fillRect 0,0,w,h clear black

    loop For each drop in drops array
        Draw->>Drop: Check y greater than canvasHeight+200
        alt Off screen
            Draw->>Drop: Reset y, visibleChars, state
            Draw->>Drop: Regenerate trail + new text
        else On screen
            Draw->>State: typingTimer += deltaTime

            alt typingState is typing
                State->>Drop: visibleChars++ every 150ms
                Note over State: Until text fully typed
                State->>Drop: Set typingState = paused
            else typingState is paused
                State->>Drop: pauseTimer += deltaTime
                Note over State: Wait 2000ms
                State->>Drop: Set typingState = resetting
            else typingState is resetting
                State->>Drop: visibleChars-- every 75ms
                Note over State: Until 0
                State->>Drop: New text, typingState = typing
            end

            Draw->>Canvas: setFont fontSize cached
            Draw->>Draw: Calculate pulse = sin globalTime

            loop For each visible character
                Draw->>Draw: Calculate decryption progress
                alt Fully decrypted over 85 percent
                    Draw->>Canvas: fillText real char bright
                else Partially decrypted 40-85 percent
                    Draw->>Canvas: fillText real or katakana
                else Encrypted under 40 percent
                    Draw->>Canvas: fillText katakana flickering
                end
            end

            opt SHOW_TRAILS enabled
                loop For each trail position
                    Draw->>Canvas: fillText katakana fading opacity
                end
            end

            Draw->>Drop: y += speed x deltaTime x 0.05
        end
    end

    Draw->>RAF: requestAnimationFrame draw

Security Observations

  • No sandbox: Required by design - the app must position windows at the desktop level, which macOS sandboxing prevents.
  • child_process.exec with AppleScript: Used in fixMacOSWindowVisibility. The script strings are constructed from hardcoded process name arrays - no user input is interpolated, so command injection risk is effectively zero.
  • shell is imported but unused in main.js:1 - minor dead code.

Typing State Machine

Each drop has a three-state cycle: typing → paused → resetting → typing

  1. typing: Characters appear one at a time (150ms interval), initially encrypted as Katakana, then "decrypting" to reveal the actual text
  2. paused: Full text visible for 2000ms, trail begins fading in
  3. resetting: Characters disappear one at a time (75ms interval), then a new word is chosen

14. Key Architectural Decisions

  1. Desktop-level window positioning: Uses setAlwaysOnTop(true, 'desktop', -1) to place the window just above the macOS wallpaper but below all apps. This is the core innovation that makes it work as a "live wallpaper."
  2. One window per display: Each connected monitor gets its own BrowserWindow with its own renderer process, allowing independent animation on each screen.
  3. Mouse event passthrough: setIgnoreMouseEvents(true) makes the window completely transparent to user interaction - clicks pass through to whatever app is underneath.
  4. AppleScript fallback: When Electron's window level APIs aren't sufficient (e.g., after Space switching), the app falls back to AppleScript via osascript to force visibility.
  5. Canvas 2D over WebGL: The animation uses the simpler Canvas 2D API rather than WebGL. This is appropriate given the relatively simple rendering requirements (text only) and maximizes compatibility.
  6. No external runtime dependencies: Zero npm runtime dependencies. Everything runs on Electron's built-in Chromium + Node.js.

Recommendations
